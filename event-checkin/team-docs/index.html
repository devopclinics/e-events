Platform credit usage standard

The methodology for how many credits any channel costs, and how a mixed-channel event gets metered against one balance. Written up 2026-07-25 after the SMS segment-cost audit in §6 exposed that the current anchor (SMS = 1 credit) is itself understated — read the sequencing note below before treating any number here as final.

The pool is fungible — there is no per-channel budget

An event has exactly one balance, event.message_credits. Every channel just debits it at that channel's own weight, in whatever mix the organizer actually sends. There is no separate "SMS budget" and "MMS budget" — 100 credits can become 100 SMS, or 33 MMS, or any combination that adds up to ≤100 credits spent. This is already how take_message_credit()/take_email_credit() work in code today; the open question is only what each channel's weight should be and why.

The standard: cost-ratio to a fixed SMS anchor

SMS is the fixed baseline. Every other channel's weight = ceil(real cost of that channel ÷ real cost of SMS), rounded to a practical credit value (or, where the ratio is far below 1, expressed as "N units per credit" the way Email already is). Reviewed whenever a provider's real rate changes — this is a formula, not a fixed table, even though the table below is today's snapshot of it.

Sequencing dependency, now applied: §6 found a full SMS send usually costs ~2 real segments (~$0.047), not the ~$0.0235 a 1-segment anchor assumes. The weights below apply that correction — SMS moves to 2 credits, the anchor a full send actually costs. WhatsApp's raw cost ratio against that corrected anchor still comes out under 1 (≈0.23–0.36x), but it's priced at 1.5 credits here as a deliberate business call, not a raw formula output — same pattern already used for MMS (3 credits vs. its raw 2.1x ratio): the formula sets a defensible floor, judgment sets the actual number above it.

Worked example — mixing channels against one balance

A Starter-tier event (100 credits) that sends 50 SMS + 10 MMS + 200 emails + 30 WhatsApp messages across the event:

Cost = (50 × 2) + (10 × 3) + (200 ÷ 10) + (30 × 1.5) = 100 + 30 + 20 + 45 = 195 credits — nearly double the 100-credit allotment. The event needs a 95-credit top-up, or to trim volume. Same per-send reserve/decline logic take_message_credit already applies today, channel by channel, as each send happens — nothing new needs building for mixed usage, only the weights (and the console to set them) need to exist.

Add-on billing architecture

Scope note: the Pricing Plans sheet (external, linked from the Media Library) is a planning draft describing the target packaging we're designing — it is not, and isn't meant to be, a description of what's live today. Nothing below should be read as "the plan is wrong because the code doesn't match it." Current code state only matters here for one reason: whatever the plan ultimately decides is a paid add-on, something has to exist to actually charge for it — and today, nothing does.

Code audit (2026-07-26): no add-on price is wired to real billing. Every paid feature is gated purely by plan_tier rank (FEATURE_MIN_PLAN in entitlements.py) — an all-or-nothing switch tied to the Event Pass tier. PricingPlan.kind only supports "tier" and "pack"; apply_purchase() only knows how to flip an event to a tier or grant credits. Even "Seat Arrangement — $1.25 per guest," the one line in §4 that reads like a real per-unit price, has zero backing code — seating_enabled is a flat tier-gate exactly like everything else. Whatever the final plan says is an add-on, this is the gap between it and a sellable reality.

⚠ SMS segment-count correction (found 2026-07-25)

The $0.0235 SMS cost above assumes one GSM-7 segment (≤160 chars). Direct inspection of backend/services/messaging.py found that every outbound SMS this app sends gets ~82 chars of fixed overhead added automatically — an 8-char "Festio: " brand prefix plus a 74-char "Reply HELP for help, STOP to opt out. Message and data rates may apply." compliance footer (_brand_sms()) — on top of a ~70-char ticket/RSVP URL (UUID tokens). Result: the invite and RSVP-link SMS templates run 216–253 chars every time, and the admission SMS is 160–200 chars depending on whether table/seat info is included. That's 2 segments, not 1, for nearly every SMS this app actually sends. Confirmed separately: take_message_credit() / channel_weight() in entitlements.py charge a flat 1 credit per SMS regardless of length — the credit system has no concept of segment count at all, so this isn't reflected anywhere in what we charge customers today.

Real cost per logical SMS send is therefore ≈$0.047 (2 × $0.0235), not $0.0235. Against the draft $0.50/SMS plan above, that only softens margin to 90.6% — still healthy. But against live, already-charging-customers-today pay-as-you-go top-up pricing (pricing_plans table: 100 credits/$6, 500/$25, 2,000/$80 → $0.06 / $0.05 / $0.04 per credit), the picture is much worse:

Top-up packRevenue / creditReal cost / SMS (2 seg.)Margin
100 credits ($6)$0.060$0.04721.7%
500 credits ($25)$0.050$0.0476.0%
2,000 credits ($80)$0.040$0.047−17.5% (loss)

The largest, best-value-looking top-up pack is currently sold at a loss on any 2-segment SMS — which, per the template audit above, is most SMS this app sends. This also means every Event Pass tier's bundled credit allotment is under-costed by roughly the same ~2x factor, though that can't be isolated to a per-credit number since tier credits are bundled into one flat price. Needs a decision: shorten the templates (drop the compliance footer's optional trailing clause, use a shorter link — e.g. a token redirect service — to claw back under 160 chars), charge 2 credits for SMS as a blanket policy, or accept the compressed/negative margin on top-ups as a low-priority cost center subsidized by tier revenue.

Open decisions

Resolved items are marked ✓. Reviewed and closed out 2026-08-02 — every item below now carries a locked decision, adopting the recommendation from the 2026-07-25/26 draft since no objection was raised against any of them.

  1. ✓ Resolved — Refund policy: no refunds, ever. Once a send is attempted, the credit is spent — regardless of provider outcome, immediate rejection, or later delivery failure.
  2. ✓ Resolved — Guest-capacity add-on blocks are Scale-only. Letting a cheaper tier buy guest blocks would let it undercut Scale's price for a similar guest count, so the 100/500-guest add-on rows in §4 only apply above Scale.
  3. ✓ Resolved — Advanced Access & Zone Control wording is written (see §4): "Standard ($99) already includes basic access zones. This add-on is the deeper Venue Access Intelligence layer (multi-zone scan, occupancy/flow/peak/journey analytics)."
  4. ✓ Resolved — Email is unlimited in customer-facing language, with an invisible anti-abuse rate limit underneath — never surfaced to organizers as a cap.
  5. ✓ Resolved — Existing customers/already-granted credits are grandfathered in place. No retroactive clawback or conversion when this restructure ships.
  6. ✓ Resolved — Bundle/credit expiry stays 30 days post-event, unchanged from current behavior.
  7. ✓ Resolved — NGN pricing is a straight FX conversion of the finalized USD figures, decided once USD is locked in.
  8. ✓ Resolved — Custom domain annual renewal is $49/year. Reflected in §4's Custom domain row.
  9. ✓ Resolved — "From $149" items now have a defined floor scope. Custom WhatsApp sender/template setup: $149 covers registration + 3 templates, $25/template after. Data import/cleanup/integration setup: $149 covers one clean file up to 2,000 records, additional records or sources quoted separately. Both reflected in §4.
  10. ✓ Resolved — Fix the SMS template length first, not the price. Shorten templates back under 160 chars (drop the optional trailing compliance clause, use a shorter token-redirect link) before considering a 2-credit SMS charge — cheapest fix, no pricing change needed unless a follow-up template audit shows it isn't enough.
  11. ✓ Resolved — Top-up amounts stay $50 / $250 / $1,000 (§3), no further changes.
  12. ✓ Resolved — Pre-send cost estimate shows both the dollar amount and the recipient count (already specified in §2b).
  13. ✓ Resolved — Deliveries/Gift/FestioMe/Guest Communication are now flat per-event service charges ($50/$50/$50/$10 — see §4), no longer included free at Starter+.

All §7 decisions are now closed. The remaining gap is entirely implementation: see §4b (add-on billing architecture — not started) and §8 (build-mapping appendix) for what has to be built before any of this is actually sellable.
