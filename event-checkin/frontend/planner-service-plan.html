Planner Service

Standalone event management suite — budget planning, vendor tracking, task timelines, day-of runsheet, and document vault. Own microservice, own DB, zero backend coupling.

New Microservice Standalone · Port 8030 FastAPI + PostgreSQL 4 Build Phases
System Design

How it fits into the stack

Planner Service follows the exact same pattern as design-service (port 8010), festiome-service (8020), and messaging-service (8001). It is:


  • A standalone FastAPI app — its own Docker image
  • Its own PostgreSQL database (planner)
  • Routed at /api/planner/ by the nginx proxy
  • Auth via the same JWT secret (validates token in every request)
  • Reads event/org identity from JWT — never calls main backend
  • Frontend pages in the existing React app under a new Planner nav tab

Zero coupling rule: planner-service never imports from backend/. It only knows event_id (from JWT or URL param) and org_id. No circular calls.

Product Scope

6 planning modules

💰

Budget

Total event budget, category breakdown, line items, estimated vs actual spend, payment status.

  • Set total budget + currency
  • Categories (Venue, Catering, AV, Flowers…)
  • Line items per category
  • Estimated / actual / paid amounts
  • % allocated, % remaining charts
  • Over-budget alerts
🏢

Vendors

Vendor directory with contacts, contracts, status pipeline, invoices, and payment records.

  • Vendor profile (name, category, contacts)
  • Status pipeline: Prospect → Shortlisted → Contracted → Paid
  • Contract upload + expiry date
  • Invoice / payment tracking
  • Rating after event
  • Notes + activity log
📅

Timeline

Pre-event planning milestones, task assignments, deadlines, and completion tracking.

  • Milestones with due dates
  • Tasks under each milestone
  • Assign to team member
  • Priority (high / normal / low)
  • % completion per milestone
  • Overdue alerts
🗓️

Runsheet

Day-of schedule with minute-level items, owner assignments, and live status tracking on the day.

  • Schedule items with start/end time
  • Owner (team member or vendor)
  • Item type (setup, program, break…)
  • Live status: upcoming / in-progress / done
  • Notes + cue fields
  • Print / PDF export
📄

Documents

Contract and document vault with status lifecycle and expiry tracking.

  • Upload contracts, quotes, proposals
  • Link to vendor or event
  • Status: Draft → Sent → Signed → Expired
  • Expiry date alerts
  • Secure download URL
📊

Dashboard

Unified planning overview — spend snapshot, vendor health, timeline progress, upcoming tasks.

  • Budget gauge (spent/total)
  • Vendor status counts
  • Tasks due this week
  • Documents expiring soon
  • Runsheet countdown
  • Event day progress

Design Decisions

Key technical choices

Auth — no new token system

planner-service shares SECRET_KEY with the main backend and validates the same JWT. The token already contains user_id and org_id. No OAuth, no service-to-service tokens in Phase 1.

Own Postgres DB, not a schema

Separate DB (not just a schema) ensures full isolation. If planner-service goes down it doesn't affect core check-in. Migration can move to shared Postgres later.

No event data duplication

planner-service stores only event_id (UUID). Event name/date are fetched by the frontend from the main API and passed as display context — not stored in planner-db.

File storage

Phase 1: local volume (/data/planner-uploads) like design-service. Phase 4: move to S3 with presigned URLs — same boto3 pattern as existing design asset uploads.

No Alembic in Phase 1

Use the same db_migrate.py auto-patch-at-startup pattern as the main backend. Fast iteration. Add Alembic when the schema is stable (after Phase 2).

Currency handling

Store all amounts as NUMERIC(14,2) in the event's declared currency. No multi-currency conversion in the service — display formatting is frontend's responsibility.
