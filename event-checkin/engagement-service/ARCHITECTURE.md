# Festio Live architecture and acceptance plan

This document is the implementation record for sections 1–62 of the Festio
Live specification. It describes what is shipped, where the boundary is, and
which advanced capabilities are intentionally extension points rather than
claims of completed product behavior.

## A. Current architecture assessment

Festio core is a FastAPI/PostgreSQL application with a React frontend and an
Nginx edge. Core owns events, organizations, users, guests, passes, RSVP,
check-in, seating, rooms, sessions, messaging, and billing. Festio Live is an
optional add-on. Core integration is limited to:

1. an event entitlement flag;
2. short-lived, event-scoped JWT minting for staff and guests;
3. a stable six-character public join code and QR generated by core;
4. a failure-isolated transactional outbox that replicates published
   Experience program sessions; and
5. frontend links that degrade to a local Festio Live error state.

Core never opens an engagement database connection and no core user request
calls the engagement API. An independent retry worker delivers versioned
program snapshots after the originating core transaction commits, avoiding
coupling where RSVP, Guest Hub, or check-in waits for Festio Live.

## B. Proposed and implemented architecture

```text
Guest Hub / Admin UI / Display browser
              |
              | optional HTTP + scoped JWT/capability token
              v
       Nginx /api/engagement
              |
              v
       engagement-service API  ---- best-effort SSE/pub-sub ---- engagement Redis
              |
              +---- durable domain data ---- engagement PostgreSQL
              |
              +---- durable analysis job --> engagement worker --> optional local AI

Festio core PostgreSQL <---- Festio core only; no engagement foreign keys or joins
             |
             +---- transactional program outbox ----> idempotent Live inbox
```

The API and worker are stateless and can be replicated. PostgreSQL is the
durable source of truth. Redis only carries transient rate-limit and realtime
signals. A normal HTTP transaction persists every answer before a best-effort
realtime publish.

## C. Failure isolation

- Core boot and user requests do not connect to or await engagement; program
  publication only appends an outbox row in the existing core transaction.
- Guest Hub renders from core data; its Festio Live entry is an optional link.
- Engagement has its own database, Redis, migration process, health probes,
  containers, volumes, worker, image, and standalone staging deploy script.
- Frontend engagement calls have ten-second bounds and remain local to the
  Festio Live screens.
- Redis failures fail open for durable submissions and clients poll HTTP every
  five seconds when SSE is unavailable.
- AI jobs are committed before the worker calls an AI provider. Provider
  failure retries and eventually marks only the analysis job failed.
- `scripts/staging_failure_acceptance.sh` stops the engagement API and worker,
  validates core UI/API surfaces, restores the exact release, and validates
  engagement recovery.

## D. Database schema

All tables live exclusively in engagement PostgreSQL. Opaque `org_id`,
`event_id`, `session_id`, `guest_id`, and `created_by` values are references,
not cross-service foreign keys.

| Aggregate | Durable tables and key guarantees |
| --- | --- |
| Activity | `engagement_activities`, event/status indexes, generic JSONB configuration |
| Questions | `engagement_activity_questions`, `engagement_question_options`, ordered and activity-owned |
| Bank | `engagement_question_bank_items`, organization scoped, archived instead of hard-deleted through the product flow |
| Participation | `engagement_activity_participants`, one guest/device per activity |
| Answers | `engagement_participant_responses`, one durable response per participant/question; retry key retained |
| Choice answers | `engagement_response_option_selections`, ordered for ranking questions |
| Public text safety | `engagement_moderation_items`, original response retained; approved-only public use |
| Q&A | `engagement_qna_questions`, `engagement_qna_upvotes`, unique participant upvotes |
| Displays | `engagement_live_displays`, unique read-only code/token, independent activity assignment |
| Branching | `engagement_activity_rules`, generic operator/action model |
| AI | `engagement_feedback_analyses`, durable queued/running/completed/failed lifecycle |
| Event defaults | `engagement_event_settings`, one record per event |
| Experience program snapshot | `engagement_program_sessions`, source-version convergence and no destructive cascade |
| Experience sync inbox | `engagement_program_sync_inbox`, one delivery ID processed once |

Migrations are append-only and owned by this service. Migration 0006 preserves
all older text responses while placing them into the safe moderation queue.

## E. API contract

All product APIs are under `/api/engagement/v1`. Staff and guests use
audience-limited JWTs. Presenter and moderator share links use explicit
capabilities. Displays use independent read-only tokens.

- Activities/questions: CRUD, guarded status transitions, advance, live state.
- Participation: join, idempotent respond, results, leaderboard.
- Question Bank: create, edit, duplicate, archive, search, category, tags,
  batch CSV import, copy into activity.
- Safety: Q&A lifecycle/upvotes and generic open-text moderation.
- Operations: conditional rules, event settings, display CRUD/control/token
  rotation, individual response drill-down, activity CSV, event analytics CSV.
- Intelligence: word cloud, durable asynchronous AI request/status.
- Realtime: scoped ticket, activity SSE, display SSE, HTTP state fallback.

## F. Event contract

Published Experience program sessions are sent as versioned
`experience.program_session.upsert` envelopes. Core commits delivery intent to
`engagement_sync_outbox`; Live records every delivery ID in an idempotent inbox
and rejects stale source versions. Archived, unpublished, or disabled source
sessions are retained with their new status, so linked questions, responses,
and displays are never deleted. Live also publishes internal realtime events
such as `activity.status_changed`, `question.state_changed`,
`response.submitted`, `qna.*`, `moderation.changed`, and `display.changed`.
No core transaction depends on delivery of any of these events.

## G. Realtime design

SSE uses one Redis channel per activity and one per display. Realtime tickets
are short-lived and scoped to an activity. Named displays subscribe to their
own channel plus the assigned activity channel. Clients reconnect naturally
and poll canonical HTTP state every five seconds, so missed pub/sub messages
do not create data loss or permanent state divergence.

## H. Frontend design

- Organizer: Overview, Activities/builder, Question Bank, Live Control,
  Displays, Responses, Analytics, Settings; program-aware tabs can be filtered
  by the synchronized Experience session.
- Guest: no extra account, pass or broadcast join, one-screen answer flow,
  safe retries, live result reveal, leaderboard, Q&A.
- Presenter/moderator: small-screen capability-scoped console with previous,
  open, pause, close, reveal, hide, show answer, next, and end controls.
- TV/projector: navigation-free responsive canvas with 21 scenes, five themes,
  independent display assignments, QR join, and polling fallback.

## I. Security and privacy model

- Every staff/guest query is event scoped; Question Bank is organization scoped.
- Owner/admin, presenter, moderator, analyst, and viewer behavior is enforced
  by role/capability checks, not by frontend route names.
- Truly anonymous activities store an HMAC pseudonym rather than guest ID or
  name. Anonymous exports and leaderboards do not reveal identity.
- Display codes/tokens are read-only, revocable, and cannot call admin APIs.
- Public endpoints are rate-limited by activity, subject, and IP.
- React escapes rendered text; SQLAlchemy parameterizes queries; CSV formula
  cells are escaped.
- Guest-authored text is retained privately but only approved moderation items
  can enter public word clouds, display scenes, or moderated AI input.

`scheduled` is currently a preparation state, not a clock-driven scheduler.
An organizer must explicitly start the activity; there is no automatic opening,
closing, timezone, or daylight-saving promise in the current API. Automatic
scheduling must add explicit start/end instants and boundary tests before it is
presented as a shipped feature.

Production uses the existing `festio-infra` Helm/ArgoCD path. The chart owns an
isolated Engagement PostgreSQL StatefulSet, Redis deployment, migration hook,
rolling API deployment, worker, Service, probes, resources, PDB, optional HPA,
backup CronJob, ServiceMonitor, and proxy route. Promotion remains deliberate;
the staging deployment scripts never modify production.

## K. Verification plan

1. Pure domain tests: transitions, validation, scoring, branching, word-cloud
   normalization, moderation flags, CSV safety.
2. HTTP wiring/security tests: every protected surface rejects missing auth.
3. Persistent staging E2E: all eight activity types, ten named participants per
   activity, 180 standard responses, moderated Q&A, five independent displays.
4. Visual E2E: organizer Overview, Live Control, Analytics, projector, guest
   list, guest revealed result.
5. Failure tests: Redis publish unavailable; AI provider unavailable; SSE
   unavailable with HTTP polling; engagement service completely stopped while
   core surfaces remain available; release restored and ready.
6. Load probe: configurable authenticated burst against the durable response
   endpoint, reporting throughput and status distribution.

## Final acceptance matrix

| Non-negotiable criterion | Implementation/evidence |
| --- | --- |
| Independent service and persistence | Own API, worker, PostgreSQL, Redis, volumes, image, migrations |
| Core starts and serves without Live | async retrying outbox only; service-down script |
| Durable answers and duplicate safety | PostgreSQL transaction, unique participant/question, idempotency key |
| No-refresh live results | SSE; HTTP polling recovery |
| Reliable presenter and independent TV | capability controls, read-only display token, visual E2E |
| Multiple simultaneous activities/displays | no event-global lock; per-activity channels and per-display state |
| Anonymous identity protection | HMAC pseudonym, no stored display name, safe export/leaderboard |
| Safe public text | approved-only moderation records; Q&A guest feed is moderated |
| Deterministic quiz scoring | pure scoring module and strategy tests |
| Redis/WebSocket/AI failure does not lose responses | persistence precedes best-effort realtime/async AI |
| Existing Festio remains operational | isolated integration plus staging stop/recovery acceptance |
